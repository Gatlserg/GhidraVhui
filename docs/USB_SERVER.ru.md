# USB-сервер C# и совместимость с клиентом

**Обновлённое состояние и режим `serve server.ini`:**
[COMPATIBILITY_STATUS.ru.md](COMPATIBILITY_STATUS.ru.md).
Ниже сохранена инструкция базового режима serve-usb.

## Что работает

Команда `serve-usb` выполняет захват физического USB-устройства и обслуживает
запросы оригинального клиента VirtualHere. Обработчики сетевого протокола и
USB написаны на C#. В режиме работы сервера `vhusbdwinw64.exe` не запускается:
используются системные SetupAPI, Newdev и WinUSB Windows.

На **VirtualHere Client 6.0.3 / протокол 8** проверены:

- обнаружение `Trust QHD Webcam` (`145F:02E7`), команда `USE` и состояние использования;
- USB control requests, чтение дескрипторов и UVC/audio-настроек;
- interrupt IN и изохронные IN-передачи;
- появление виртуальной камеры Windows со статусом `OK`;
- чтение настоящего **MJPEG-кадра 640×480** через Media Foundation с виртуального устройства;
- `STOP USING`, удаление виртуальной камеры и восстановление физической камеры.

Это испытание одной модели на одном компьютере через TCP loopback.
Для других USB-устройств и версий клиента совместимость нужно проверять отдельно.
Bulk и isochronous OUT реализованы, но реальным устройством в этом тесте не проверены.
Компактный вариант изохронных ответов проверен по восстановленной схеме;
живой клиент в испытании использовал обычные `0x24` / `0x25`.

## Запуск

Нужна Windows x64. Откройте PowerShell **от администратора** и из корня `vhui`:

```powershell
& ".\dotnet\artifacts\recovery\win-x64\Vhui.Recovery.exe" serve-usb 145F:02E7 17570
```

Сервер работает до `Ctrl+C`. По умолчанию он слушает `127.0.0.1`.
В оригинальном клиенте добавьте вручную `127.0.0.1:17570`, выберите
`Trust QHD Webcam` у `Vhui C# USB server` и нажмите использование устройства.
Перед выходом можно нажать `Stop Using`; `Ctrl+C` также отменяет запросы
и восстанавливает драйвер захваченного устройства.

Форма команды:

```text
serve-usb <VID:PID> <port> [seconds=0] [bind-IP=127.0.0.1]
```

`seconds=0` означает работу до остановки. Для ограниченного теста задайте
1–3600 секунд. Например, слушать указанный интерфейс или все IPv4-интерфейсы:

```powershell
& ".\dotnet\artifacts\recovery\win-x64\Vhui.Recovery.exe" serve-usb 145F:02E7 17570 0 0.0.0.0
```

На другом компьютере в клиенте укажите IP компьютера-сервера и тот же порт.
Правила Windows Firewall автоматически не добавляются. Транспорт — обычный
TCP без TLS и аутентификации; выбирайте интерфейс доверенной локальной сети.
Соединение с отдельного компьютера в текущем испытании не проверялось.

Экспортируется одно устройство с указанными VID/PID; совпадение должно быть
единственным. Одновременный захват другим соединением отклоняется.
USB-хабы этим backend не поддерживаются.

## Драйверы и освобождение

На сервере временно снимается стандартный драйвер именно выбранного физического
устройства, затем устанавливается системный `winusb.inf`. После освобождения
Windows снова выбирает совместимый штатный драйвер. В испытании камера
возвращалась к `usbccgp` / `usbvideo` со статусом `OK`.

Клиенту нужен его собственный виртуальный USB-драйвер. Во время эталонного
испытания оригинальный клиент установил подписанный `vhusb3hc`; он остаётся
установленным для последующих подключений. Сервер C# собственный kernel driver
не устанавливает. Пока устройство захвачено, оно недоступно локальным приложениям
на физическом компьютере как обычная камера.

Сведения для восстановления сохраняются **до смены драйвера** рядом с EXE:
`usb-leases/*.json`. При нормальном завершении `Phase` становится `Restored`.
Если процесс аварийно завершён во время захвата, выполните от администратора:

```powershell
Get-ChildItem ".\dotnet\artifacts\recovery\win-x64\usb-leases\*.json"
& ".\dotnet\artifacts\recovery\win-x64\Vhui.Recovery.exe" restore-usb "<полный путь к журналу JSON>"
```

Повторный захват при незавершённом журнале блокируется до восстановления.
Журнал содержит исходный INF, instance ID и прежний `DeviceInterfaceGUID`.
Он нужен для восстановления после принудительного завершения, которое не даёт
программе выполнить обычный cleanup. Требование перезагрузки Windows не скрывается.

## Повторить проверку

После `dotnet/Build.ps1 -Publish` выполните в повышенном PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\dotnet\scripts\Test-UsbClient.ps1 -HoldSeconds 8 -VideoProbe
```

Перед запуском закройте другие экземпляры клиента: его IPC-канал общий.
Скрипт создаёт собственный конфиг, выключает Auto-Find, захватывает только
вебкамеру, читает видеокадр, освобождает устройство и ждёт завершения сервера.
Фотография на диск не сохраняется: отчёт содержит размер кадра и SHA-256.

Отчёты: `dotnet/artifacts/usb-client-test/`:

| Файл | Содержание |
| --- | --- |
| `result.json` | Захват, получение кадра, освобождение и восстановление физической камеры |
| `virtual-frame.json` | Путь именно виртуального устройства, MJPEG, разрешение, размер и хеш кадра |
| `captured.xml`, `held.xml`, `after.xml` | Состояние устройства по API оригинального клиента |
| `server.log` | Коды запросов/ответов C# и причины ошибок |
| `client.log` | Журнал клиента |

Большие payload в обычном журнале опускаются (`DataOmitted: true`), чтобы запись
видео не тормозила изохронные передачи. Сохраняются тип и размер сообщения.
Для исследования оригинального сервера существует `trace-proxy`: он пишет
декодированные сообщения в BIN до общего лимита 128 MiB, продолжая пересылку.
Это вспомогательный инструмент анализа, не реализация USB backend.

## Границы реализации

Базовая команда serve-usb выбирает одно устройство. Новый режим serve с INI
поддерживает несколько устройств, TLS/reverse, mDNS, политики доступа и службу.
GUI доступен в отдельном Vhui.Server.exe. EasyFind, vhfilter и полное удалённое
администрирование пока не перенесены.
WinUSB ограничивает выбор конфигурации устройства; произвольное переключение
нескольких конфигураций не поддерживается. Нет обещания совместимости со всеми
классами USB, поведения после физического отключения во время передачи и
длительного видеостриминга на произвольном оборудовании. На тестовой камере
проверены две минуты видео и аудиозахват; результаты приведены в новом отчёте.

Схемы сообщений сверены с кодом оригинала и независимыми захватами его обмена.
Двоичные эталоны находятся в `tests/Vhui.Recovery.Tests/Fixtures/`.
