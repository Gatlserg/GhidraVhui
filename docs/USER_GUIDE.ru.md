# Vhui.Recovery — руководство пользователя

Для работы через окно используйте **Vhui.Server.exe**:
[руководство GUI](GUI.ru.md). Он публикуется в `artifacts/server/win-x64`.

**INI, несколько устройств, TLS/reverse, mDNS и служба Windows:**
[COMPATIBILITY_STATUS.ru.md](COMPATIBILITY_STATUS.ru.md).
Пример server.example.ini поставляется рядом с EXE.

## Для чего нужна утилита

`Vhui.Recovery.exe` — консольная утилита для исследования исходного EXE,
чтения настоящих USB-дескрипторов и проверки переноса сетевого протокола на C#.
Режим `serve-usb` захватывает устройство через WinUSB и выполняет URB оригинального
клиента VirtualHere. На клиенте 6.0.3 проверено получение MJPEG-кадра с виртуальной
вебкамеры и восстановление физического устройства после освобождения.
**Запуск USB-сервера и границы совместимости:** [USB_SERVER.ru.md](USB_SERVER.ru.md).
Подробное сопоставление с оригиналом и его неочевидные функции описаны
в `analysis/FEATURE_COMPARISON.ru.md` в дереве исходников.

Доступные команды:

| Команда | Действие | Результат |
| --- | --- | --- |
| `inspect <EXE>` | Проверяет SHA-256 и заголовки EXE, определяет расположение и параметры LZMA | Текстовый отчёт в консоли; файлы не создаются |
| `extract-payload <EXE> <новый BIN>` | Проверяет EXE, декодирует подтверждённые данные LZMA, сверяет SHA-256 результата | Двоичный файл размером **11 470 339 байт** |
| `usb-inspect <VID:PID>` | Читает дескрипторы физического устройства через USB-хаб Windows | JSON со строками, device/configuration descriptors и ошибками |
| `probe-server <host> <port>` | Посылает информационные команды протокола VirtualHere | JSON с описанием сервера и полученными сообщениями |
| `serve-discovery <VID:PID> <port> [seconds]` | Показывает одно физическое устройство клиенту через `127.0.0.1` | Информационный сервер на 60 секунд по умолчанию; журнал JSON в stderr |
| `serve-usb <VID:PID> <port> [seconds=0] [bind-IP]` | Захватывает устройство и обслуживает USB-запросы клиента | Нужны права администратора; остановка — `Ctrl+C` |
| `serve <server.ini>` | Сервер с общим реестром, конфигурацией, TLS/reverse и mDNS | Настройте server.example.ini; права администратора для захвата |
| `service-install <server.ini>` | Устанавливает VhuiRecovery в SCM | Затем service-start; управление: service-status/service-stop/service-uninstall |
| `usb-check <host> <port> <VID:PID>` | Захватывает устройство для сравнительной пробы протокола и освобождает его | JSON с запросами и ответами; используйте на тестовом устройстве |
| `restore-usb <journal.json>` | Восстанавливает драйвер после аварийного завершения захвата | Нужны права администратора; журнал рядом с EXE в `usb-leases` |
| `camera-probe <name>` | Читает один видеокадр через Windows Media Foundation | JSON с форматом, размером и хешем; файл изображения не создаётся |

Запуск без аргументов выводит краткую справку. Имена команд вводятся строчными
буквами, как в таблице. Команды `inspect` и `extract-payload` читают EXE как
данные и не запускают его. USB-команды работают в Windows и читают реальные
дескрипторы через системные API.

## Проверить вебкамеру и сетевой обмен

Из корня `vhui`:

```powershell
& ".\dotnet\artifacts\recovery\win-x64\Vhui.Recovery.exe" usb-inspect 145F:02E7
& ".\dotnet\artifacts\recovery\win-x64\Vhui.Recovery.exe" serve-discovery 145F:02E7 17575 60
```

`145F:02E7` — шестнадцатеричные VID/PID обнаруженной `Trust QHD Webcam`.
Для другого устройства укажите его VID/PID. Серверу нужно ровно одно совпадение.
Он слушает только `127.0.0.1`, не устанавливает драйвер и не переключает
стандартный драйвер камеры. Длительность — от 1 до 3600 секунд.

Пока сервер работает, во втором терминале:

```powershell
& ".\dotnet\artifacts\recovery\win-x64\Vhui.Recovery.exe" probe-server 127.0.0.1 17575
```

В оригинальном клиенте добавьте сервер вручную: `127.0.0.1:17575`.
Ожидается сервер `Vhui C# (discovery only)` и устройство `Trust QHD Webcam`.
В режиме `serve-discovery` камера не захватывается. Для использования устройства
запускайте `serve-usb` по инструкции [USB_SERVER.ru.md](USB_SERVER.ru.md).

Воспроизводимая проверка с оригинальным клиентом 6.0.3:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\dotnet\scripts\Test-DiscoveryClient.ps1
```

Перед тестом закройте другие экземпляры клиента: его IPC-канал общий.
Скрипт использует `analysis/client/recovered/vhui64.exe`, собственный конфиг,
отключает Auto-Find, получает `GET CLIENT STATE` и `LIST`, сравнивает
идентификаторы и названия с физическим USB-устройством. Команду `USE` не посылает.
После проверки он закрывает созданные им процессы. Отчёты находятся в
`dotnet/artifacts/discovery-test/`: `result.json`, `client-state.xml`,
`client-list.txt`, `hardware.json`, `server.jsonl`.

Проверка на этом компьютере прошла: производитель `SC`, название `Trust QHD Webcam`,
серийный номер `202001010001`, четыре интерфейса, первый интерфейс класса Video (`14`).
В отчёте отдельно зафиксировано `VideoTransferTested: false`.

## Как запустить

Готовая Windows x64-сборка находится в исходном дереве по пути:

```text
dotnet\artifacts\recovery\win-x64\Vhui.Recovery.exe
```

Откройте PowerShell или терминал VS Code. При двойном щелчке по EXE программа
выведет справку и завершится; открывшееся консольное окно может сразу закрыться.

Для переноса на другой компьютер скопируйте **всю папку `win-x64`**, включая DLL.
Отдельная установка .NET, SDK, Java или Ghidra для готовой сборки не требуется.
В этой же папке лежит копия руководства — `README.ru.md`.

Все примеры следующего раздела выполняются **из корня `vhui`**, где находятся
папки `dotnet` и `analysis`.

## Пример 1. Проверить исходный EXE

```powershell
& ".\dotnet\artifacts\recovery\win-x64\Vhui.Recovery.exe" inspect ".\analysis\recovered\vhusbdwinw64.exe"
```

Ожидаемый вывод:

```text
Проверен исходный vhusbdwinw64.exe (UPX / LZMA / Windows x64).
Поток: смещение в файле 0x21F, размер 0x3249E0.
LZMA: lc=3, lp=0, pb=2.
Лимит из C: 11470341; подтверждённый декодируемый префикс: 11470339 байт.
```

Что означают эти значения:

| Поле | Значение |
| --- | --- |
| `0x21F` | Смещение начала сжатого потока от начала EXE, **543 байта** |
| `0x3249E0` | Длина исследуемого сжатого диапазона, **3 295 712 байт** |
| `lc`, `lp`, `pb` | Параметры декодирования LZMA; утилита читает их из EXE |
| `11470341` | Предел выходного размера, указанный в декомпилированном C |
| `11470339` | Размер префикса, подтверждённого независимым декодером |

`inspect` проверяет соответствие известной сборке и структуру PE.
Декодирование и проверка содержимого результата выполняются командой
`extract-payload`.

## Пример 2. Извлечь данные

```powershell
& ".\dotnet\artifacts\recovery\win-x64\Vhui.Recovery.exe" extract-payload ".\analysis\recovered\vhusbdwinw64.exe" ".\dotnet\artifacts\payload.bin"
```

Папка назначения должна существовать, а **файла `payload.bin` ещё не должно быть**.
При повторном запуске выберите новое имя, например `payload-2.bin`.

Ожидаемый вывод:

```text
Сохранён проверенный префикс payload: 11470339 байт.
Это данные для анализа, а не исполняемая программа и не реализация USB-сервера.
```

Полученный `.bin` содержит декодированные байты для дальнейшего исследования.
Его можно открыть в HEX-редакторе или использовать при анализе структуры данных.
Сам по себе этот файл не восстанавливает заголовки, импорты и релокации исходной
программы. Переименование `.bin` в `.exe` не превращает его в рабочую программу.

В C указан предел на **два байта больше** подтверждённого префикса. Утилита
сохраняет только проверенные данные; недостающие байты не дописываются.
Полный распакованный PE был получен отдельно официальным UPX и находится
в исходном дереве: `analysis/recovered/vhusbdwinw64.unpacked.exe`.

### Проверить сохранённый файл

```powershell
(Get-Item -LiteralPath ".\dotnet\artifacts\payload.bin").Length
Get-FileHash -LiteralPath ".\dotnet\artifacts\payload.bin" -Algorithm SHA256
```

Размер должен быть `11470339`, SHA-256:

```text
61945CC7B89351313683F74257EF9FC0AA0D49A0823E67E0F9901FEA9AE19067
```

## Если папка с утилитой перенесена

Откройте PowerShell в папке `win-x64` и передайте полный путь к исходному EXE:

```powershell
& ".\Vhui.Recovery.exe" inspect "C:\files\vhusbdwinw64.exe"
& ".\Vhui.Recovery.exe" extract-payload "C:\files\vhusbdwinw64.exe" ".\payload.bin"
```

Относительные пути считаются от **текущей папки терминала**. Для путей с пробелами
используйте кавычки. Имя входного файла может отличаться: проверяется содержимое.

## Какой входной файл поддерживается

Профиль команд `inspect` и `extract-payload` привязан к одной исследованной
сборке. USB-команды этим профилем не ограничены. Ожидаемый SHA-256 входного EXE:

```text
6AE762D598800F0F11BA4F317F09697177A569BADA586CC518BAABFC4E043EEC
```

Подходящий файл уже восстановлен в `analysis/recovered/vhusbdwinw64.exe`.
Другая версия VirtualHere, изменённый EXE, распакованный EXE, C/H-файлы или GZF
будут отклонены. Расположение данных в других сборках утилита автоматически
не определяет.

## Ошибки и коды завершения

После запуска в PowerShell код завершения доступен через `$LASTEXITCODE`.

| Код | Значение |
| --- | --- |
| `0` | Команда успешно выполнена либо справка выведена при запуске без аргументов |
| `1` | Ошибка данных, USB, сети, чтения или записи; `usb-inspect` также возвращает 1 при отсутствии устройства или наличии ошибок в JSON |
| `2` | Неизвестная команда либо неверное количество аргументов; выводится справка |

| Сообщение / ситуация | Что проверить |
| --- | --- |
| `SHA-256 не совпадает` | Нужен исходный упакованный EXE именно исследованной сборки |
| Файл не найден | Путь и текущую папку терминала |
| Файл назначения уже существует | Укажите новое имя выходного `.bin` |
| Папка назначения не найдена | Создайте папку либо выберите существующую |
| Отказано в доступе | Доступ на чтение входа и запись в выбранную папку |
| Ошибка заголовка PE или границ LZMA | Соответствие файла профилю и его целостность |

При ошибке записи, например нехватке места, в назначении может остаться
неполный файл. Проверяйте код завершения, размер и хеш; для повторного извлечения
используйте другое имя. Входной EXE утилита открывает для чтения.

## Что относится к библиотеке C#, а не к командам EXE

В `Vhui.Core` также перенесены:

- `ServerConfiguration`: поиск настроек без учёта регистра, значения по умолчанию,
  подстановки переменных окружения, разбор числового префикса как у Windows `strtol`.
- `UsbStringDescriptorCodec`: формирование буфера запроса к USB-хабу и проверка
  уже полученного ответа; `UsbStringDescriptor` декодирует текст UTF-16.

`WindowsUsbInventory` вызывает SetupAPI и информационные IOCTL USB-хабов;
это реальное чтение устройства. `UsbStringDescriptorCodec` отвечает за буфер
одного запроса. `VirtualHereFrameCodec` читает TCP-кадры, в том числе LZ4,
а `VirtualHereServer` реализует информационный обмен и подключение USB backend.

`WinUsbDeviceLease` выполняет привязку к WinUSB, асинхронные передачи и возврат
штатного драйвера. `WindowsUsbProtocolSession` реализует захват/освобождение,
control/bulk/interrupt/isochronous URB и отмену выполняющихся запросов.
Проверено штатное освобождение; восстановление после физического отключения
во время передачи требует дополнительных испытаний. Служба Windows реализована;
GUI доступен в отдельном Vhui.Server.exe. Проверены аварийный выход с recovery и двухминутный поток.
Первый обычный запуск оригинального сервера вернул ошибку Windows 740.
Последующий штатный запуск через UAC успешно повысил права тестового процесса:
сервер 4.8.8 запустился, C#-утилита получила сведения по протоколу 8.
Отчёт: `dotnet/artifacts/native-elevated-test/result.json`, ответ — `probe.json`.
Скрипт `dotnet/scripts/Test-NativeServerElevated.ps1` выполняет информационный
тест в повышенном процессе и останавливает созданный сервер после проверки.
Повышение всей сессии IDE не требуется: достаточно запустить сам USB-сервер
или тестовый PowerShell-процесс через UAC. Backend захвата теперь реализован.
